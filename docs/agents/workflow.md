# Workflow

How a change is made, checked and handed over.

## Before writing code

- Read the code you are about to change, and its tests. Many odd-looking
  lines are deliberate: read the module's docstring before "simplifying"
  anything. The `SceneFX/` docstrings record the crashes each effect is
  built to avoid.
- For a FreeCAD feature (a Part Design operation, a property), read
  FreeCAD's wiki page and its source. Property names, enumeration values
  and node names come from FreeCAD, not from memory.
- For Coin, read Coin's documentation or source for the node you use:
  many nodes behave differently inside FreeCAD's render action.
- If the request is ambiguous in a way that changes what you build, ask
  one question. Otherwise pick the conventional answer and say so.

## While writing

- Make the smallest change that does the job well. Don't refactor
  neighbouring code unasked; mention it instead.
- Match the patterns already in the codebase (see
  [architecture](architecture.md)). Reuse `Utils/` before writing a new
  helper.
- If an attempt doesn't fix the problem, **revert what it added** before
  trying something else. Don't stack speculative fixes.
- When the fastest solution costs readability or adds much code, stop
  and lay out the options with their pros and cons. The maintainer
  decides.
- New and rewritten modules meet the full standard and pass the checks in
  [testing](testing.md). Older code is not reformatted wholesale: it is
  brought up to the standard when it is rewritten for a reason.

## Git

- The maintainer creates branches, commits, merges and pushes.
- An assistant may run read-only git only (`status`, `log`, `diff`,
  `show`), with `--no-optional-locks` in a shared working copy.
- Hand over with a suggested commit message: a short imperative subject
  (`area: what changed`), a body saying why, wrapped at 72 columns.
- A user-visible change gets a line in `CHANGELOG.md`; a release bumps
  `package.xml`'s version and date.

## Files that stay out of the repository

- Scratch models, test documents and experiments go in `local/`, kept out
  by `.git/info/exclude`. Keep a generator script there rather than only
  the `.FCStd`.
- No binaries that can't be reviewed, apart from the images and icons in
  `Resources/` (icons are generated by `tools/icons/gen.py`).

## Reporting back

- Lead with the outcome, then what changed, then what is left.
- State how it was verified: unit tests, `freecadcmd`, or a running
  FreeCAD. Never imply a GUI check that didn't happen.
- Name anything you noticed but did not change.
